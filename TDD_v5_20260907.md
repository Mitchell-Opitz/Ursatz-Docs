# TECHNICAL DESIGN DOCUMENT v5 — General-Purpose Computational Music Platform

**Classification:** Foundational Architecture / Implementation Contract
**Supersedes:** v4. Condensed — every section retained in substance, verbose "shall" scaffolding and repeated examples collapsed into reference tables/lists. Phase-1 objects that now have their own detailed specs (Domain Spec v4, API Contract v4, Canonical IR v3, Dependency & Layer Spec v3, Test Spec v3) are pointed to rather than re-derived here; this document remains the source for everything else, especially Phases 2–18 which have no other home yet.

**Primary Objective:** a theory-neutral computational foundation for representing, observing, interpreting, analyzing, transforming, generating, performing, rendering, importing, exporting, querying, and studying musical material — without any theory, notation system, storage technology, or generation technology defining the underlying musical domain.

---

## Executive Summary

Not a software implementation of any particular theory of music. Represents musical material independently of: theory, notation, instrument, tuning, performance, recording, database, serialization, rendering tech, analytical methodology, ML architecture, generation algorithm, language.

**Central principle:** distinguish what musical material *is* from what is *observed* about it, what is *inferred*, how it's *interpreted*, under which *framework*, how it's *transformed*, how it's *rendered/performed*.

```
SOURCE/WORLD → OBSERVATIONS → CANONICAL MUSICAL MODEL → (events, structures, relationships)
  → CONTEXT → INTERPRETATIONS → THEORY/KNOWLEDGE → (analysis, generation, transformation)
  → CANONICAL MUSICAL MODEL → (notation, performance, audio)
```

No layer above the canonical model may silently redefine it. No interpretation may silently become fact. No uncertainty may be discarded for downstream convenience. No generated object may lose lineage. No external format may become the domain model merely because it's convenient to serialize.

## Architectural Objective

Optimize for: semantic correctness, theory neutrality, representational completeness, extensibility, provenance, uncertainty preservation, explainability, reproducibility, interoperability, testability, long-term maintainability, controlled performance optimization. Initial implementation prioritizes semantic correctness over throughput; optimization is evidence-driven.

## Architectural Thesis

Explicitly distinguish: Musical Material, Notation, Performance, Recording, Observation, Interpretation, Theory, Rule, Constraint, Preference, Heuristic, Statistical Model, Transformation, Generation. These may reference one another but never collapse into one universal object — reject "Note = notation symbol = MIDI message = performed sound = scale degree = chord member." Instead: a musical occurrence *may be* notated as / performed as / recorded as / observed as / interpreted as — each a distinct, optional projection.

## The 25 Foundational Laws (normative)

1. **Musical Material Is Not Theory** — a framework may interpret material but not define its existence.
2. **Representation Is Not Interpretation** — a representation of an event doesn't imply its meaning.
3. **Notation Is Not Musical Reality** — notation is a representation/documentation of material.
4. **Performance Is Not Symbolic Content** — realization may differ from symbolic content.
5. **Recording Is Not Performance Semantics** — a recording is captured signal; meaning derived from it is observation/interpretation.
6. **Relationships Are First-Class** — important relationships aren't encoded solely as ad hoc fields.
7. **Context Matters** — context-dependent claims must explicitly identify that context.
8. **Interpretation Is Non-Authoritative by Default** — analytical claims don't silently overwrite source material.
9. **Uncertainty Is Data** — unknown, ambiguous, competing, and probabilistic information stays representable.
10. **Provenance Is Preserved** — derived objects retain lineage sufficient to determine how they were produced.
11. **Theory Is Pluggable** — the kernel doesn't depend on any particular music-theoretical framework.
12. **Rules and Statistics Are Different** — a statistical tendency never automatically becomes a theoretical rule.
13. **Constraints and Preferences Are Different** — a preference ranks candidates without invalidating them.
14. **External Formats Are Adapters** — MIDI/MusicXML/ABC/MEI/audio/DB/JSON/protobuf don't define the canonical domain.
15. **Storage Is Not Domain Semantics** — any storage technology remains replaceable.
16. **Identity Is Not Position** — array index, measure number, file offset, row number are never sole identity.
17. **Occurrence Is Distinct from Conceptual Identity** — a recurring motif and one occurrence of it are different concepts.
18. **Written and Sounding Pitch Are Distinct** — instrument transposition isn't embedded into the universal pitch definition.
19. **Symbolic Time Is Exact** — authoritative symbolic time doesn't depend on floating-point arithmetic.
20. **Transformations Do Not Mutate Their Inputs** — they create new versions or derived objects.
21. **Stochastic Processes Are Reproducible** — random generation supports explicit seeds and reproducibility metadata.
22. **Loss Is Explicit** — conversions that can't preserve information report the loss.
23. **Canonicalization Is Not Equality** — two objects may canonicalize equivalently without being identical entities.
24. **Partial Information Is Valid Information** — an incomplete object is representable when the domain permits incomplete knowledge.
25. **The Foundation Remains Small** — new concepts are introduced above the kernel whenever possible.

## Domain Boundaries

World/Source, Digital Artifact, Musical, Representation, Observation, Interpretation, Theory/Knowledge, Transformation, Generation, Performance, Query, Corpus, Persistence. These are architectural boundaries, not merely organizational ones.

- **World/Source:** external artifact/phenomenon (manuscript, score, recording, live performance, MIDI stream, audio file, annotation, corpus, database, external analysis). Has identity and provenance; never assumed complete or authoritative.
- **Digital Artifact:** an external digital object (PDF, MusicXML, MIDI file, MEI, WAV, JSON, image, DB export) — stays distinguishable from the musical material it represents.
- **Canonical Musical Domain:** represents material independently of serialization (Event, Occurrence, Container, Structure, Pitch, Duration, MusicalTime, Voice, Instrument, Relationship) — requires no JSON/XML/SQL/MIDI.

## Domain Object Categories

Entity, Value, Occurrence, Event, Container, Structure, Relationship, Assertion, Observation, Hypothesis, Interpretation, Context, Framework, Rule, Constraint, Preference, Heuristic, Tendency, Procedure, Activity, Evidence, Provenance, Intent, Candidate, Transformation. Different semantics — never implemented as interchangeable generic records for convenience.

## Identity & Versioning

*Phase-1 slice (EntityID, NoteEvent, Voice, references) is fully specified in Domain Specification v4 and API Contract Specification v4 — not re-derived here.*

- **Entity** — identifiable conceptual object (Work, Instrument, Voice, Motif, Phrase, Framework, Rule, TransformationDefinition). Persistent entities normally have: id, type, schema_version, metadata, provenance_reference.
- **Value** — immutable content, identity = value (Duration, MusicalTime, PitchClass, PitchSpelling, Interval, MeterSignature, Tempo, Ratio, Frequency).
- **Occurrence** — one situated instance of something (MotifOccurrence, PhraseOccurrence, ThemeOccurrence, PerformanceOccurrence, NotationOccurrence). A motif may exist abstractly while occurrences identify concrete regions.
- **Event** — an occurrence tied to a temporal domain (NoteEvent, RestEvent, TempoEvent, MeterChangeEvent, ControlEvent). May be instantaneous or extended; not every event reduces to onset+duration.
- **Event Identity** — stable, independent of measure number, voice position, array index, MIDI tick, file location.
- **Event Lifecycle** — creation, revision, derivation, supersession, deletion/tombstoning. Deletion from an application view doesn't necessarily destroy provenance.
- **Version Model** — identity and version are distinct (`EntityID=M1, Version=4`). A revision (`M1 v4`) and a derived object (`M2 derived_from M1`) are not the same thing.

## Temporal Architecture

Time is explicitly multidimensional: MusicalTime, NotatedTime, AbsoluteTime, PerformanceTime, AudioTime — never assumed interchangeable. (MusicalTime/Duration/TimeSpan Phase-1 detail: see Domain Spec v4.)

- **MusicalTime** — exact rational symbolic position.
- **Duration** — amount of time, `>= 0`, exact rational.
- **TimeSpan** — `{start, end, boundary semantics}`; boundary may be closed/open/left_closed/right_closed where distinctions matter. Preferable to assuming every object is onset+duration.
- **Instant** — some events (tempo change, meter change, key-signature declaration, control message, structural boundary) have no meaningful duration; `TimeInstant` is separate from `TimeSpan`.
- **Temporal Anchors** — objects may anchor by absolute/relative/container-relative/event-relative position, notation position, or performance timestamp; the anchor type must be explicit.
- **Relative Time** — relationships like "after Event A by 1/8" needn't convert to absolute position prematurely.
- **Meter / MeterMap** — meter (4/4, 3/4, 6/8...) is independent of duration and doesn't itself determine all temporal semantics; a MeterMap associates meter with temporal regions (`region, meter_signature, effective_from, optional beat structure/hierarchy`).
- **Metrical Position** — measure_index/beat/subdivision/metrical_level/beat_strength/local_position are contextual coordinates, not intrinsic time properties.
- **Notated Position** — distinct from MusicalTime; may include document/page/system/staff/measure/layer/symbol index/graphic coordinates. A notation document may encode multiple temporal interpretations.
- **Tempo / TempoMap** — tempo is modeled independently of symbolic time; a TempoMap maps `musical_time → performance_time`, representing tempo changes, accelerando, ritardando, rubato, curves, performance deviations.
- **PerformanceTime** — realized coordinates (onset/release timestamp, inter-onset interval, timing deviation, local tempo); never overwrites symbolic MusicalTime.
- **AudioTime** — positions in captured signal space (sample index, frame index, seconds); distinct from PerformanceTime.
- **Temporal Mapping** — mappings between time dimensions (MusicalTime↔PerformanceTime, MusicalTime↔NotatedPosition, PerformanceTime↔AudioTime) are first-class where needed; may be exact, approximate, piecewise, or uncertain.

## Pitch Architecture

Decomposed into independent dimensions: PitchIdentity, PitchClass, PitchSpelling, PitchRealization, TuningSystem, Frequency, PitchTrajectory. (PitchIdentity/PitchSpelling Phase-1 detail: see Domain Spec v4.)

- **PitchClass** — equivalence under a *declared* equivalence relation; never assumed to mean modulo-12.
- **PitchRealization** — sounding/physically realizable pitch (frequency, ratio, cents, fundamental, custom tuning coordinate).
- **TuningSystem** — independent (12-TET, 24-TET, Pythagorean, Just Intonation, Meantone, custom ratio, non-octave, microtonal); never hard-codes A440.
- **PitchTrajectory** — `{time, pitch realization, uncertainty}` for continuous pitch variation (vibrato, glissando, pitch bend, portamento, microtonal drift) without corrupting symbolic pitch.
- **WrittenPitch/SoundingPitch** — distinguished; an instrument transposition mapping may connect them.
- **Instrument** — higher-level entity with configurable range, tessitura, transposition, clefs, articulations, techniques, dynamics, continuous controls, polyphony, physical constraints, preferred registers.
- **InstrumentCapability** — modeled separately from instrument identity where practical (`pitch_range, simultaneous_note_limit, articulation_support, technique, physical_constraints`), allowing one instrument multiple playing contexts.

## Events, Containers & Structures

Foundational event set stays small: NoteEvent, RestEvent, ControlEvent. (NoteEvent Phase-1 detail: Domain Spec v4.)

- **RestEvent** — explicit symbolic absence in context; not universal physical silence.
- **ControlEvent** — temporal changes not naturally modeled as notes (pedal, control change, continuous control, program change, performance instruction); protocol-specific concepts stay adapter-specific unless promoted.
- **Event Attachments** — articulation, dynamic, ornament, tie, slur, pedal, accent, expression, technique, notation, performance realization — attachable, not baked into NoteEvent as a universal attribute bag.
- **Ties** — represented as relationship/semantic objects, not merged note events — preserves notation, symbolic identity, performance realization, and analysis semantics as separate concerns.
- **Slurs** — independent of ties; may indicate phrasing, legato, performance instruction, analytical grouping, or notation depending on context.
- **Articulation/Dynamics** — modeled as attachments/event-level semantic objects, kept distinguishable from their performance realization.
- **Voice** — logical stream/simultaneity domain; does not automatically imply instrument, staff, part, harmony, or melodic role (Phase-1 detail: Domain Spec v4).
- **Part, Staff, Layer, Voice** — distinguished, not universally equivalent: a voice may appear on multiple staves; a staff may contain multiple voices; a part may contain multiple staves.
- **Containers** — group/organize objects (Voice, Layer, Staff, Part, Measure, Phrase, Section, Movement, Work); containment is explicit and theory-neutral.
- **Structures** — organize material at higher semantic levels (Motif, Figure, Phrase, Theme, Section, Movement, Work); may reference events without duplicating them. Structure does not imply hierarchy — a work needn't follow Motif→Phrase→Theme→Section as a universal shape; hierarchical structure is optional.
- **Occurrences of Structures** — a structure may be abstract while occurrences are situated (Motif M1 → occurrences O1, O2 at specific event ranges), enabling pattern/form analysis without duplicating events.

## Notation, Performance & Recording

- **Score Model** — specialized representation layer (Staff, Clef, Key Signature, Time Signature, Measure, Beam, Stem, Barline, Tuplet, Layout, Page, System); doesn't redefine canonical events.
- **Notation Model** — treated as a document/representation model, not merely a renderer; may hold information with no canonical-event equivalent (engraving decisions, page layout, graphic coordinates, beaming, stem directions, editorial markings, facsimile references, variant readings, source-document structure). MEI is the relevant precedent: its scope covers structured musical documents, metadata, notation, analysis, performances, linking — not just abstract notes.
- **Performance Model** — a realization of material: performance events, actual onset/release, velocity, pitch realization, timing deviation, dynamic/articulation realization, pedal state, continuous controls, performer metadata.
- **Performance Event** — references its symbolic source where known (`realizes NoteEvent N1`), but the relationship may be 1:1, 1:many, many:1, or unknown — essential for ornamentation, arpeggiation, splitting, merging, repeated attacks, imperfect transcription.
- **Recording** — captured signal (`channels, sample_rate, duration, encoding, source, metadata`); not itself a musical interpretation.
- **Recording-to-Music Mapping** — audio analysis produces Observation → Candidate → Interpretation → Canonical Representation, preserving uncertainty throughout.

## Semantic Layer

Derived/framework-independent musical concepts: Interval, Sonority, Contour, RhythmicPattern, PitchCollection, Scale. `Chord`/`Key` require explicit contextual/framework semantics and aren't automatically foundational facts. A derived semantic object identifies its source/derivation (e.g. `Interval I1 {endpoint_a, endpoint_b, derivation}`) and may be materialized for query/cache/analysis/indexing without becoming source truth.

- **Interval** — supports directed/undirected, diatonic/chromatic distance, quality, compound, microtonal, ratio, cents, framework-specific interpretation; identifies which dimensions are actually known.
- **Sonority** — a selected collection of simultaneously-relevant pitch-bearing events, with explicit selection semantics (time window, voice set, performance vs. symbolic events). Not automatically a Chord.
- **Chord** — a semantic interpretation of a sonority under a declared framework/context (`Sonority S1 → Interpretation{claim: C-major triad, framework: tonal-harmony}`).
- **Key** — contextual; a note doesn't intrinsically contain scale degree/tonic function/Roman numeral — these are derived relative to context.
- **Scale** — an ordered pitch collection under declared semantics (`root, ordered pitch collection, interval pattern, tuning, framework, orientation`).
- **Scale Degree** — contextual; requires target, context, framework, and mapping to assert.
- **Contour** — relative pitch change (up/down/same/up-up-down); computable independently of exact pitch.
- **Rhythmic Pattern** — independently representable; a rhythmic query needs no pitch information.

## Relationships

First-class model: `Relationship {id, source, predicate, target, scope, context, qualifiers, evidence, uncertainty, provenance}`.

- **Predicate** — has metadata: `{name, inverse, symmetric, transitive, allowed_source_types, allowed_target_types, contextual}` — prevents implicit relationship semantics.
- **Initial vocabulary** (extensible): contains, contained_by, precedes, follows, overlaps, coincident_with, derived_from, transformed_from, realizes, resembles, contrasts_with, interpreted_as, supports, contradicts, occurs_in, belongs_to, instantiates, has_occurrence.
- **Scope** — global, work, movement, section, phrase, measure, voice, event, performance, analysis.
- **Validity** — `valid_from, valid_until, context, framework, version` — relationships change as interpretations/versions change.

## Interpretation & Uncertainty

- **Assertion** — a claim by an agent/process ("Note N belongs to phrase P"); distinct from the objects it describes.
- **Observation** — records detected/measured info (`{id, subject, property, value_or_candidates, method, source, uncertainty, timestamp, provenance}`) without implying interpretation.
- **Hypothesis** — a candidate explanation (possible key, chord, motif match, spelling); supports multiple candidates.
- **Uncertainty** — first-class object: unknown, interval estimate, probability distribution, confidence score, candidate set, credible interval, qualitative uncertainty, competing hypotheses. A scalar confidence is not the universal model.
- **Candidate Set** — e.g. `{C#: .73, Db: .19, C: .08}` — probabilities need not sum to one unless the model says so explicitly.
- **Unknown vs. Low Confidence** — "unknown," "known approximately," and "known candidates with probabilities" are distinct semantics.
- **Interpretation** — `{target, claim, framework, context, evidence, uncertainty, author, method, status, provenance}`.
- **Status** — proposed, supported, accepted, rejected, superseded, user_confirmed, machine_generated, imported, disputed, unknown — configurable.
- **Competing Interpretations** — multiple coexist (e.g. C major vs. E minor vs. modal reading of the same material); no global winner required.

## Context

- **Context** — conditions under which an assertion is evaluated (tonal, metrical, instrument, performance, historical, analytical, theoretical framework, local structural).
- **Composition** — contexts nest/compose (Work → Movement → Section → Phrase → Event); a child may inherit while overriding, with explicit inheritance rules.
- **Resolution** — determining applicable contexts, precedence, inherited properties, overrides, conflicts, unknown values.

## Theory & Rules

- **Framework** — an interpretive system (Common-Practice Harmony, Species Counterpoint, Jazz Harmony, Schenkerian Analysis, Set Theory, Neo-Riemannian, Modal Theory, custom). Consumes canonical domain interfaces; never modifies foundational objects for theory-specific semantics.
- **Framework Versioning** — every nontrivial framework is versioned (`framework_id, framework_version`); rule evaluations record the version used.
- **Rule** — formal evaluative statement (e.g. "parallel fifths prohibited") defining framework, scope, conditions, evaluation, severity, explanation, version.
- **Constraint** — restricts candidate states (hard/soft/weighted/conditional/contextual); machine-evaluable for generation.
- **Preference** — ranks candidates without necessarily invalidating them (e.g. "prefer stepwise motion").
- **Heuristic** — a strategy/estimate (e.g. "favor likely cadential continuation"); never represented as universal truth.
- **Tendency** — observed statistical behavior (e.g. "transition X→Y occurs frequently in corpus C"); never automatically implies must/must-not/valid/invalid.
- **Statistical Model** — explicit object (`input_features, output, probability, training_corpus, model_version, calibration`); its output doesn't automatically become a theory rule.
- **Procedure** — an algorithmic method (Roman numeral analysis, cadence detection, phrase segmentation, motif search, species generator); declares inputs, outputs, configuration, version, dependencies, determinism.
- **Rule Evaluation** — `{rule, target, context, result, severity, evidence, explanation, evaluator, evaluator_version}`; result ∈ {pass, fail, warning, unknown, not_applicable}.

## Evidence & Provenance

- **Evidence** — structured basis for an assertion (observed pitch, interval relationship, voice-leading pattern, corpus statistic, user annotation, scholarly source, rule result, ML prediction); distinguishable from the interpretation it supports. Has strength, relevance, reliability, independence, method, source — no single scalar score required.
- **Provenance** — modeled explicitly (not a text field), conceptually following Entity/Activity/Agent/Derivation/Attribution/Association — aligned with, though not required to literally implement, W3C PROV.
  - **Activity** — a process producing/changing information (import, normalization, analysis, transformation, generation, OCR, audio transcription, manual editing, export).
  - **Agent** — human, software, organization, ML model, external source.
  - **Derivation** — `{output, input, activity, parameters, agent, software_version, framework_version, timestamp}`.
  - **Event-level provenance** — transformations preserve source↔output event mappings, including one-to-many (e.g. ornamentation).
  - **Provenance Graph** — normally acyclic; cycles prohibited unless a future model explicitly supports them.
  - **Audit History vs. Provenance** — provenance answers "where did this come from," audit history answers "who changed what, when, why." Both may be required.
- **Authored Content** — human-authored analysis stays identifiable (`{author, target, claim, context, framework, timestamp}`); a user accepting a machine interpretation doesn't erase its machine origin.
- **Promotion** — a derived result may be promoted to authored content, retaining the machine hypothesis, the user action, timestamp, original evidence, and original provenance.

## Equality, Canonicalization & Partial Information

Five distinct notions, tested independently (full test treatment: Test Spec v3): **Identity Equality** (same entity/version), **Value Equality** (same semantic value), **Structural Equality** (equivalent structure under declared rules), **Semantic Equality** (equivalent despite differing representation, e.g. under different tuning/context), **Canonical Equality** (same normal form under a *versioned* normalization policy).

**Canonicalization** must not destroy meaningful distinctions (e.g. C#/Db must not collapse if the distinction matters to notation/theory). **Partial Information** — objects support partial knowledge (`pitch=unknown`, `pitch_candidates=[...]`) rather than forcing placeholders to masquerade as facts.

## Canonical IR, Serialization & Persistence

*Full Phase-1 treatment: Canonical IR Specification v3.* The IR represents content via domain semantics, not transport syntax, and must support: exact time, exact duration, multiple tuning systems, multiple pitch representations, stable identity, partial information, relationships, contexts, provenance, versioning, extensions.

- **Serialization** — object → external syntax (JSON, protobuf, CBOR, XML, binary); no format defines domain semantics. Canonical serialization provides schema version, stable identifiers, deterministic field ordering, exact rational values, explicit null/unknown semantics, extension mechanism, canonical ordering, migration support.
- **Serialization vs. Persistence** — object→representation vs. object→durable storage; kept distinct.
- **Storage Independence** — the domain doesn't depend on Postgres/MongoDB/Neo4j/SQLite/event-sourcing/object-storage; any may sit behind repository interfaces.
- **Persistence Model** — mature architecture: Canonical Object Store + Relationship Store + Search Indexes + Corpus Analytical Store + Blob Storage. Phase 1 uses the simplest implementation preserving semantics.
- **Repository Interfaces** — EventRepository, EntityRepository, RelationshipRepository, StructureRepository, InterpretationRepository, ProvenanceRepository — storage implementations stay replaceable.
- **Transaction Boundaries** — operations creating related objects (e.g. a Transformation's output + provenance activity + relationships) need explicit consistency — no output without its mandatory lineage.
- **Caching** — cache keys must include all semantic dependencies (`object_id, object_version, analyzer_version, framework_version, context_hash, configuration_hash`).

## Query Architecture

Applications use domain queries (`find_notes(region)`, `find_intervals(sequence)`, `find_occurrences(motif)`, `find_interpretations(target)`, `find_relationships(subject)`) rather than exposing SQL. Each query specifies input domain, selection/ordering/context/uncertainty/version semantics.

- **Pattern Matching** — operates over declared dimensions (interval sequence, rhythm).
- **Similarity** — must declare its dimensions explicitly (exact pitch, pitch class, interval sequence, contour, rhythm, transposition/inversion/retrograde/RI, approximate pitch/rhythm) — no generic undeclared `similarity()`.
- **Search Result** — `{target, match region, similarity, criteria, evidence, provenance, context}`.
- **Views** — derived (Temporal, Pitch, Rhythmic, Voice, Harmonic, Motivic, Formal, Performance, Notation) reference canonical data rather than duplicating it.

## Transformation Architecture

Explicit domain operations: Transposition, Inversion, Retrograde, RetrogradeInversion, Augmentation, Diminution, Fragmentation, Expansion, Contraction, Displacement, Ornamentation. Every transformation declares input type, parameters, output type, preserved/modified dimensions, mapping behavior, validation, provenance, determinism — and where practical is referentially transparent (`Transform(input, params) → output`, inputs never silently mutated).

- **Transposition** — defines pitch displacement, spelling behavior, tuning behavior, range policy, instrument context.
- **Inversion** — defines axis, pitch space, spelling policy, tuning semantics (axis=C4 ≠ axis=first_note).
- **Retrograde** — explicitly states what's reversed (event order, pitch sequence, rhythmic sequence, articulation sequence, or all attributes).
- **Augmentation/Diminution** — specifies which temporal dimension is modified (durations, inter-onset intervals, structural timing, notation values, performance timing); default symbolic behavior doesn't touch performance timing unless requested.
- **Ornamentation** — not merely a pitch transformation; may map one event to many, requiring provenance to support one-to-many derivation.
- **Validation** — every transformation tests input compatibility, parameter validity, domain invariants, instrument constraints, output validity, provenance completeness.

## Analysis Architecture

Pipeline: Input → Normalization → Observation → Feature Extraction → Candidate Generation → Context Resolution → Interpretation → Evidence → Uncertainty → Result. Analysis never mutates source material merely by producing an interpretation.

- **Analyzer Interface** — `analyze(input, context, configuration) → AnalysisResult{observations, candidates, interpretations, evidence, uncertainty, provenance}`.
- **Feature Extraction** — explicit features (pitch interval, pitch class, contour, duration, metrical position, density, voice crossing, register, sonority); cacheable but remain derived.
- **Candidate Generation** — distinguishes observed fact / candidate / interpretation (e.g. pitches C-E-G observed → C-major sonority candidate → tonic-harmony-in-C-major interpretation).
- **Harmonic Analysis pipeline** — Canonical Events → Sonority Extraction → Key/Chord Hypotheses → Context Resolution → Framework Evaluation → Interpretations → Evidence → Uncertainty.
- **Motif Analysis** — produces Motif, Occurrence, SimilarityResult, Evidence — never duplicates matched events.

## Generation Architecture

Planning-based pipeline: Intent → Normalization → Context Resolution → Constraint Extraction/Normalization → Conflict Detection → Generation Plan → Candidate Generation → Candidate Evaluation → Validation → Selection → Canonical Material → Provenance.

- **Intent** — natural language compiles to `Intent{purpose, target, style, context, meter, length, constraints, preferences, source_material}`; NL never directly manipulates the IR.
- **Constraint Normalization** — Intent → Extraction → Normalization → Conflict Detection → Executable Constraint Set.
- **Constraint Conflict** — reported explicitly, never silently dropped (e.g. hard range constraint vs. preference for large leaps vs. user-required octave leap).
- **Priority vs. Severity vs. Weight** — distinct, not synonyms.
- **Candidate** — `{material, evaluations, violations, score, provenance}`, a proposed result before final acceptance.
- **Candidate Evaluation** — via hard constraints, rules, preferences, heuristics, statistical models, user feedback; results stay explainable.
- **Generator** — `generate(plan) → CandidateSet`; declares supported inputs/outputs, configuration, constraints, determinism, version. Generators may compose (ThemeGenerator → PhraseGenerator → BasicIdeaGenerator) with an explicit inter-level interface.
- **Hierarchical Generation** — operates at motif/basic-idea/phrase/theme/section/movement/work — a generation strategy, not a universal ontology.
- **Stochastic Generation** — accepts `random_seed`; preserves seed, generator_version, configuration, input_ids, framework_version.
- **Reproducibility** — distinguishes bitwise / implementation / semantic reproducibility (Law 21) — exact bit-for-bit reproduction across incompatible implementations isn't promised.
- **Human-in-the-Loop** — feedback becomes structured info (constraint, preference, annotation, ranking signal, rejection reason) — never directly mutates a generated result without an explicit operation.
- **Machine Learning** — an interchangeable provider producing Observation/Prediction/Candidate/Probability/Embedding/Feature/Score; the domain doesn't depend on a particular ML framework.
- **Neural Generation** — preferred pipeline: Structured Intent → Neural Model → Candidate Structures → Symbolic Validation → Theory Evaluation → Ranking → Canonical Representation. Direct MIDI generation isn't a foundational requirement.
- **Practice Generation** — `PracticeRequest{instrument, technique, skill_level, pitch_context, rhythmic_context, duration, difficulty} → Canonical Representation → notation/MIDI/audio`.
- **Difficulty** — multidimensional (pitch, rhythm, range, articulation, technical, cognitive, reading, tempo, coordination); a scalar difficulty is a derived summary, not foundational truth.
- **Ear Training** — uses foundational semantic objects (`IntervalRequest{interval, direction, context, repetitions}`), sharing the interval model with analysis/theory.

## I/O, Corpus, and Loss

- **I/O Architecture** — input adapters (MIDIImporter, MusicXMLImporter, MEIImporter, ABCImporter, AudioAnalyzer, OCRImporter); output adapters (MIDIRenderer, MusicXMLRenderer, MEIRenderer, NotationRenderer, AudioRenderer) — all communicate with the canonical domain through explicit mapping layers.
- **OCR pipeline** — Image → Visual Recognition → Notation Recognition → Observations → Candidates → Validation → Canonical Representation; uncertainty stays attached.
- **Audio pipeline** — Recording → Signal Processing → Feature Detection → Observations → Candidate Events → Contextual Interpretation → Canonical Representation; retains uncertainty and source linkage.
- **MIDI Boundary** — MIDI (1.0 or 2.0/UMP) doesn't define the core model; channels/ticks/message structure are transport concepts. Mapping NoteEvent→MIDI may lose spelling, analytical meaning, exact notation, non-MIDI tuning, structural semantics — loss must be reported.
- **MusicXML/MEI Boundary** — remain external representations; notation-specific info that can't safely reduce to canonical events stays available through a notation/document layer (MEI's scope — structural, notational, analytical, performance, linking — is the relevant precedent).
- **Loss Model** — conversions report preserved/converted/approximated/discarded/unknown per field.
- **Round-Trip Semantics** — distinguishes byte-identical, structural, canonical, and semantic round-trip, and lossy round-trip — not every format supports byte-identical reconstruction.
- **Corpus Architecture** — pipeline Corpus Source → Import → Normalization → Canonical Representation → Feature Extraction → Indexing → Statistics; corpus statistics never mutate foundational music. Records corpus_version, importer_version, normalizer_version, feature_extractor_version, analysis_version, configuration. Every corpus-derived claim traces to corpus, documents, normalization, feature extraction, analysis procedure, configuration.

## Plugins & Security

- **Plugin Architecture** — plugins may provide theory frameworks, analysis algorithms, generators, transformations, importers, exporters, ML providers, visualizations.
- **Plugin Contract** — declares plugin_id, version, capabilities, dependencies, configuration_schema, supported_frameworks, input/output types, permissions.
- **Plugin Dependency Rules** — a plugin may depend on lower-level interfaces but never alters foundational semantics for its own theory's convenience; a plugin repeatedly needing a missing foundational abstraction triggers an architecture review.
- **Plugin Security** — untrusted plugins don't automatically get filesystem/network/process/database/credential access; mitigated via sandboxing, process isolation, capability APIs, resource limits, permission declarations.
- **External Input Security** — MIDI, MusicXML, MEI, PDF, images, audio, archives, serialized objects, plugins, scripts, ML models, user-defined rules, external corpus data are all hostile-input boundaries; parsers must be hardened and fuzz-tested.
- **Declarative Rules** — user-created rules preferably use a declarative language (`{framework, scope, predicate, severity, explanation}`); arbitrary executable code isn't the default rule representation.
- **Query Safety** — resource limits, pagination, max recursion depth, timeout, memory limits — especially for large corpora and relationship traversal.

## Module Architecture & Dependency Direction

*Full treatment: Dependency & Layer Specification v3 (layer order, cross-cutting modules, prohibitions, Registry-first rule, both formerly-open issues resolved).* Initial modular monolith: music-core, music-identity, music-time, music-pitch, music-events, music-containers, music-structure, music-semantics, music-context, music-relationship, music-interpretation, music-provenance, music-theory, music-rules, music-analysis, music-transform, music-generation, music-query, music-performance, music-notation, music-io, music-corpus, music-security. Dependencies point toward foundational abstractions (identity → core → time/pitch → events → containers/structures → semantics/relationships → context/interpretation → theory → analysis/transformation/generation → I/O/applications); notation and performance may depend on canonical abstractions but never redefine them. Theory leakage is forbidden at the type level (Pitch must never know SpeciesCounterpoint; NoteEvent must never contain RomanNumeral; Duration must never know BeethovenStyle) — the correct shape is `SpeciesCounterpointFramework consumes Canonical Musical Interfaces`.

## Application & Validation Architecture

Applications (Composition, Practice, Ear Training, Analysis, Corpus, OCR, Audio, Notation, Performance) consume domain services and never implement duplicate music semantics.

Validation occurs at several levels: schema, object, domain invariant, relationship, context, framework, constraint, serialization, rendering, security.

- **Domain Invariants** (examples): Duration ≥ 0; time values valid; pitch conforms to declared model; relationship endpoints valid; entity IDs unique; required provenance exists; transformation outputs valid; canonical serialization valid; version references valid.
- **Relationship Invariants**: source/target exist; predicate exists and permits source/target type; required context/provenance exists.
- **Provenance Invariants**: ancestor/activity/agent references exist; mandatory derivation edges exist; cycles prohibited where DAG semantics are declared.
- **Framework Validation** stays isolated — a rule evaluation (e.g. First Species Counterpoint's Parallel Fifth rule failing on a VoicePair) never modifies the notes it evaluates.
- **Transformation Validation** — parameter validity, domain compatibility, invariant preservation, provenance, event mapping, output validity.

## Testing, Observability, Reproducibility

*Full Phase-1 test treatment: Test Specification v3.* Required categories: Unit, Property-Based, Invariant, Golden, Serialization, Migration, Round-Trip, Relationship, Provenance, Context, Theory, Transformation, Analysis Regression, Generation Validation, Corpus Regression, Performance, Security, Fuzz.

- **Golden Tests** — critical transformations get version-controlled expected outputs including provenance (e.g. transpose C-E-G by +P5 → G-B-D).
- **Migration Tests** — every schema migration tests old-input → migration → new-canonical-form, deterministically.
- **Analysis/Generation Regression** — representative corpora retained; algorithm changes must make result differences visible. Generation regression verifies constraints satisfied, required provenance exists, seed recorded, result structurally valid — exact output equality only where determinism is contractually guaranteed.
- **Security Testing** — parser fuzzing, malformed serialization, malicious XML, zip bombs, oversized files, resource exhaustion, plugin isolation, rule injection, query abuse.
- **Observability** — structured logs, traces, metrics, analysis/generation/correlation/provenance IDs — must never alter domain semantics.
- **Reproducibility Record** — `{activity_id, input_ids, input_versions, algorithm_version, framework_version, configuration, random_seed, environment info where needed, output_ids}`.
- **Determinism** — analysis should be deterministic wherever practical; generation may be stochastic; a non-deterministic algorithm must state why in its reproducibility contract.

## Style & Formal Analysis

**Style** is not merely a rule list — it's `{frameworks, constraints, preferences, tendencies, probability_models, formal conventions, instrumentation, harmonic vocabulary, rhythmic vocabulary}`, contextual and versioned. A statistical style model may state `P(X|context)=0.72` but never automatically "X is valid" or "X is required." **Formal analysis** produces contextual interpretations (e.g. "measures 1–8 = antecedent, framework = sentence-period theory") without altering the underlying events.

## Worked Examples (condensed)

The canonical worked example (C4-E4-G4 triad, its competing interpretations, and its +P5 transposition with provenance) is fully specified in Canonical IR Specification v3 — not repeated here. Other illustrative patterns from this document, condensed to their point:

- **Ambiguous spelling** — an audio pitch estimate of "≈C#" retains both C#/Db candidates until context (e.g. surrounding key) resolves one; the original observation stays intact regardless.
- **OCR** — a recognized note is an `Observation` with weighted candidates, not a `NoteEvent`, until an explicit resolution step promotes it.
- **Harmonic ambiguity** — one Sonority may carry multiple simultaneously-valid Interpretations (C major chord / I in C major / VI in E minor) with no forced resolution.
- **Motif search** — a search result is a `Match{region, similarity, criteria, evidence}`, not automatically a confirmed motif occurrence.
- **Counterpoint** — Cantus Firmus → Species Framework → Constraints → Candidate Generation → Rule Evaluation → Ranking → Validation → Canonical Material; the Species framework stays outside the kernel throughout.

## Work Model

Distinguishes Work, Edition, Arrangement, Revision, Performance, Recording, Analysis — a work and its realizations are not identical; same work / different edition / different arrangement / different performance / different recording may all coexist without collapsing into one object. **Source Variants** eventually support variant reading, editorial decision, source disagreement, uncertain reading, without forcing one source to be universally authoritative. **Scholarly Annotation** supports `{claim, target, author, source, citation, framework, evidence, uncertainty, date, status}`.

## Extension Mechanism

New semantic concepts preferably enter as framework-defined semantic objects, relationships, interpretations, procedures, or annotations — not by modifying core classes. **Core Extension Rule:** a new concept enters the foundational kernel only if (1) framework-neutral, (2) required by multiple subsystems, (3) not reasonably representable as an extension, (4) semantically stable, (5) introduces no theory leakage.

## Architecture Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Scope explosion | tiny kernel, phased development, vertical slices, extension boundaries |
| Ontology explosion | prefer relationships, derive values, use contextual interpretations, avoid theory-specific core classes |
| Theory leakage | dependency architecture tests, framework isolation |
| Interpretation becomes fact | observation/hypothesis/interpretation/evidence/uncertainty/provenance pipeline |
| Notation contamination | canonical model + separate notation/document model |
| Performance contamination | symbolic event model + separate performance realization model |
| Time model failure | exact rational symbolic time + explicit anchors + tempo mappings + performance time |
| Pitch model failure | identity + spelling + realization + tuning + trajectory, kept separate |
| Provenance explosion | compact references, lazy expansion, indexed lineage |
| Graph overuse | first-class relationships + ordinary storage initially + graph optimization only when justified |
| Serialization becomes architecture | domain-first design |
| Identity confusion | entity identity + version + occurrence + provenance, kept distinct |
| Uncertainty collapse | unknown + candidate sets + probabilistic models + competing hypotheses |
| ML contamination | ML output enters only through Observation/Candidate/Prediction/Score contracts |
| Plugin security | capabilities, sandboxing, resource limits |

## Final Recommendation

The architecture freezes around: a small foundational kernel + exact symbolic time + general pitch/tuning model + explicit events/occurrences/containers/structures + first-class relationships + context + observation/hypothesis/interpretation/evidence/uncertainty + provenance + theory frameworks/rules/constraints/preferences/heuristics/statistical models + pure transformations + analysis + generation + notation/performance/recording + I/O adapters + storage abstraction. The system does **not** attempt to freeze every future musical concept — it freezes the semantic rules governing how new concepts are introduced. The kernel stays intentionally small.

## Ultimate Architectural Objective

The platform is not "software that knows music theory." It is **a general-purpose computational language and platform for representing musical material, temporal organization, pitch, events, structures, relationships, observations, interpretations, context, evidence, uncertainty, provenance, theoretical frameworks, transformations, constraints, performances, notation, recordings, and generation processes** — able to represent what exists, what occurred, where/when, how it's organized, what relates to what, what was observed/hypothesized/interpreted, under which framework, with what evidence and uncertainty, by whom/what process, from which source, through which transformation, under which constraints, according to which model, and with what resulting realization — all kept computationally distinguishable.

**Governing principle:** Freeze the semantics of the foundation, not the ontology of every future musical idea. Keep the kernel small; make relationships, context, interpretation, uncertainty, provenance, and extension mechanisms first-class; preserve the distinctions between symbolic material, notation, performance, and recording; and ensure no theory, storage system, notation format, statistical model, or generation technology can become the definition of music.
